# 限流

## 问题

要按调用方限制请求频率，保护上游，也防止一个 Key 把网关的连接池占满。网关跑多个实例，额度必须是所有实例共享的一份，不能各算各的。

麻烦在于限流天生和时间有关，而"和时间有关"的东西难写出确定的测试：断言"放行了多少个请求"，结果会随机器快慢浮动。

## 方案

**令牌桶，状态放在 Redis 里，补充和扣减在一个 Lua 脚本里做完**（`internal/ratelimit/ratelimit.go`）。桶里记两个字段：剩下多少令牌、上次补充是什么时候。每个请求取一个令牌，取不到就拒。

桶容量等于每分钟的额度，补充速率是额度除以 60 秒，所以攒得下一分钟的突发，之后按平均速率放行。

**为什么必须是一个脚本。** 拆成"读令牌数 - 算补充 - 写回"三步的话，两个实例会读到同一个令牌数、各扣一个，这一个令牌就被用了两次。Redis 执行 Lua 期间不处理其他命令，所以脚本内部是原子的。测试用两个 `Limiter` 共用一套 Redis、480 个并发打同一个桶，断言放行的总数正好是额度（`TestConcurrentCallersShareOneBucket`）。

**当前时间由网关传进来**，不是脚本里取 Redis 的时钟，见 [ADR-0004](../adr/0004-per-key-token-bucket.md)。测试注入一个只在 `advance` 时才往前走的时钟，于是"用光 60 个令牌、前进 30 秒、正好再放行 30 个"是一句确定的断言。代价是实例之间的时钟漂移，NTP 之下通常十毫秒级，对按分钟补充的桶来说可以忽略。脚本里对经过的时间取了 `math.max(0, now - ts)`，时钟往回跳时不会把令牌算没。

**额度是每个 Key 一个值**，存在 `api_keys.rpm_limit`，为 0 时用配置里的默认值。额度和身份一起进鉴权缓存，限流时不用再查数据库。

**桶的键 5 分钟没人用就删掉。** 这个时间比装满一个桶还长，所以删掉的一定是已经满了的桶，下次再来时按"桶是满的"重新开始，和留着它是一回事。

**被拒时返回 429 `rate_limit_exceeded`，带 `Retry-After`**：脚本顺带算出还差多少令牌、按当前速率要等多少毫秒。

**`ratelimit` 不认识 `apikey`。** 中间件接一个 `Caller` 函数，由 `cmd/gateway` 提供：从 context 里取出鉴权结果，额度用 Key 自己设的，没设就用配置里的默认值。业务包之间不互相 import，和 `billing` 与 `relay` 的处理是一样的。

**收口断言**分两层。`internal/ratelimit` 用注入的时钟断言精确的令牌行为；`cmd/gateway` 用真实时钟跑端到端：把 Key 的额度设成每分钟 6 个，300 个并发请求正好放行 6 个。端到端这里额度取小是有意的——额度 6 意味着每 10 秒才补回一个令牌，而整个测试跑完不到一秒，补充的量远不足一个，放行数就是个确定的数。额度取 60 时每秒补一个，测试慢一点就会多放行一个，这一点是实测出来的。

## 取舍

- **令牌桶，不是滑动窗口。** 令牌桶允许突发（桶是满的时候可以一口气用掉一分钟的量），这对 LLM 调用是合理的：调用方常常是批量发一组请求再等结果。滑动窗口计数更严格，但要么存一串时间戳（内存随额度涨），要么用两个窗口做近似。
- **Redis 不可用时放行。** 脚本执行失败只记一条日志，请求照常通过，见 [ADR-0002](../adr/0002-balance-in-postgres-only.md)。限流是保护上游的，不是记账的：放过几个请求的代价，比 Redis 一抖动整个网关就不可用要小。为此 Redis 的超时压到 100 毫秒并关掉重试，否则"放行"会变成"每个请求先慢几秒再放行"。
- **额度的单位是请求数，不是 token 数。** 按 token 限流更贴近上游的真实限制，但一次请求用多少 token 要等它结束才知道，而限流必须在请求开始前做决定。真要按 token 限，得预扣 token 再退，那就是计费那套逻辑再来一遍。
- **桶是按 Key 的，不按模型、不按 IP。** 按模型限流要给每个模型一个桶，键变成 `<key>:<model>`，实现上只是多一个维度，但配置和管理接口都要跟着长。现在用不到。

## 延伸问题

- 调用方拿到 429 之后立刻重试会怎样？`Retry-After` 已经给了确定的等待时间，遵守它就不会空转。不遵守的话，每次重试都会走一遍脚本，但脚本本身很便宜。
- 额度改小之后，已经攒在桶里的令牌怎么办？脚本每次都用传进来的容量做上限，所以下一个请求就会把令牌数压到新容量以内。改大则是立刻可以攒到新上限。
- 为什么不用 go-redis 自带的 `redis_rate`？它实现的是 GCRA，行为和令牌桶接近，但这个项目要讲清楚限流是怎么算的，自己写一段十几行的 Lua 比引一个依赖更值。
- 多个网关实例之间时钟漂移大了会怎样？漂移体现为补充的令牌略多或略少。真要消除，把脚本里的 `now` 换成 `redis.call('TIME')` 即可，桶的数据结构不用动——代价是测试重新变得不确定。
