# 鉴权缓存

## 问题

每个请求都要先认出调用方是谁。Key 的明文不落库，鉴权就是拿明文的 SHA-256 去 `api_keys` 查一行。这是一次等值查询，走唯一索引，本身不慢，但它出现在每一个请求的最前面，而且和后面的预扣、结算抢同一个数据库连接池。

同时还有一条硬要求：**管理员禁用一个 Key 之后，下一个请求就该被拒**，不能等缓存过期。网关会跑多个实例，禁用是在其中一个实例上发生的。

## 方案

**Cache-Aside，缓存放在 Redis 里**（`internal/apikey/cache.go`）。鉴权先查 `auth:<hash>`，没有就查数据库再写回，TTL 5 分钟。

**缓存里只放 `Identity`**：Key 的 ID、禁用状态、限流额度。余额不进缓存——余额只有 PostgreSQL 一份，见 [ADR-0002](../adr/0002-balance-in-postgres-only.md)。这条界线让缓存变成纯粹的加速：里面的数据全丢了也只是慢一点，不会算错账。

**查不到的 Key 也记进缓存**，TTL 30 秒。不然拿随机 Key 反复打过来，每个请求都要查一趟数据库，缓存等于没有。

**禁用之后立刻删缓存**（`internal/admin/admin.go`）。顺序是先改数据库、再删 Redis 的键。删的是那份共享的缓存，所以不用在实例之间广播：另一个实例的下一个请求发现缓存没了，自然回源，读到的就是禁用后的状态。改额度和创建 Key 时同样删一次——创建之前可能有人拿这个哈希查过，缓存里记着"不存在"。

**Redis 出任何问题都当缓存不存在**：读失败、写失败、存的值解析不出来，都只记一条日志，然后走数据库。Redis 整个连不上时网关照常工作，有测试守着（`TestGatewayKeepsWorkingWithoutRedis`）。

**Redis 的超时压到 100 毫秒，并且关掉重试。** 这条比"失败时放行"更要紧：按 go-redis 的默认值，一个连得上但不响应的 Redis 会让每个请求先等 5 秒、还重试 3 次，网关比根本没有缓存时慢得多。放行的前提是很快就知道 Redis 不行了。

**收口断言**（`cmd/gateway/main_test.go`）：两个实例共用一套 Redis，各跑一次请求把 Key 灌进缓存，在第一个实例上禁用，然后两个实例的下一个请求都必须返回 401 `key_disabled`。断言里特意区分了错误码——预扣的条件 UPDATE 也会挡下被禁用的 Key，但那时返回的是 429 `insufficient_quota`，说明禁用是被计费兜住的，而不是鉴权挡下的。

## 取舍

- **回填有竞态，没有消除它。** 一个请求读到旧值、还没写回 Redis 时，管理员禁用并删了缓存，这个请求随后把旧值写了回去，禁用就要等一个 TTL 才生效。消除它要用版本号或者 `WATCH`，而代价不值得：被禁用的 Key 即使穿过鉴权，也会在预扣的条件 UPDATE（`WHERE ... AND NOT disabled`）上被挡下，只是调用方收到的是 429 而不是 401。钱不会错，错的只是错误码。
- **TTL 5 分钟，不做主动刷新。** 充值不删缓存——余额不在缓存里，充完立刻就能用。只有改变身份的操作（禁用、改额度）才删。
- **缓存"不存在"的代价是新建的 Key 可能要等 30 秒。** 只有"先查后建"这个顺序才会踩到，而管理接口创建 Key 时会顺手删掉这个记号，所以实际上碰不到。
- **不做进程内缓存。** 加一层本地缓存能省掉 Redis 的往返，但禁用就得在实例之间广播（发布订阅或者版本号轮询），"立即失效"这条断言会难保证得多。Redis 的一次 GET 在同机上是几十微秒，先不换这个复杂度。

## 延伸问题

- Redis 挂掉的瞬间，所有请求一起回源数据库，会不会把数据库压垮？会有一个尖峰。挡它的常见做法是 singleflight：同一个哈希只放一个请求去查数据库，其余等结果。现在没做，因为鉴权查询走唯一索引、很轻。
- 缓存里存 JSON 是不是浪费？一个 `Identity` 编码出来不到 50 字节，省的那点空间不值得换一个自定义编码。
- 要不要缓存整个 `Key`（含余额）？不要。那样余额就有两份，得回答"以谁为准"，而这正是 ADR-0002 要避免的。
