# 预扣与结算

## 问题

一次请求花多少钱，要等请求结束才知道：流式回答可能持续几十秒。如果等结束再扣，同一个 Key 的并发请求在余额耗尽之前会全部放行，余额被打穿；而且网关要跑多个实例，它们之间不能靠进程内的锁来协调。

同时还要保证：请求被中途断开也要落账；同一个请求不能被扣两次钱。

## 方案

**转发前预扣，结束后结算。** 规则写在 [ADR-0001](../adr/0001-reserve-then-settle.md)，这里说实现。

**预扣是一条带条件的 UPDATE**（`internal/billing/store.go`）：

```sql
UPDATE api_keys SET balance_micro = balance_micro - $1
WHERE id = $2 AND NOT disabled AND balance_micro >= $1
```

判断和扣减在同一条语句里完成，没有"先查再改"的空档。同一个 Key 的并发预扣由这一行的行锁排队，后到的语句看到的已经是扣过的余额。扣成功与否看 `RowsAffected`：0 表示余额不够或者 Key 被禁用，请求直接返回 429，不会发往上游。

`RowsAffected` 在 MySQL 上默认数的是"改动了几行"，所以连接串里开了 `clientFoundRows`，让它数"WHERE 匹配到几行"。差别在免费模型上会咬人：单价为 0 时预扣金额是 0，这条 UPDATE 什么也没改动，按默认语义会被当成余额不够，请求平白被拒（见 [ADR-0006](../adr/0006-mysql-instead-of-postgres.md)）。

**预扣的金额按最大可能的费用算**：估算的 prompt token × 输入单价 + 输出上限 × 输出单价。调用方没指定输出上限时，网关取模型的默认值，并把它写进发往上游的请求，这样上游生成的内容不会超过预扣时的假设。

**结算在一个事务里做两件事**：把预扣和实际费用的差额退回余额、写一条用量记录。用量记录以请求 ID 为主键，重复结算时这条 INSERT 撞主键，整个事务回滚，刚退的那笔钱跟着撤销，余额只被退一次。请求 ID 由网关生成，调用方传来的不采用。

**这两句的先后是定死的：先退余额，再写记录。** 反过来写会死锁——`usage_records` 上有指向 `api_keys` 的外键，InnoDB 校验外键时先在父行上加共享锁，紧接着的 UPDATE 又要把同一行升级成排他锁，同一个 Key 的并发结算于是各拿着共享锁等对方放手。收口断言那 1000 个并发里实测 2% 撞上 `Error 1213`，换成"先取排他锁"之后连跑五轮零死锁。这条和判断"已经结算过"的方式都是换数据库换出来的，见 [ADR-0006](../adr/0006-mysql-instead-of-postgres.md)。

**结算放在 `defer` 里。** 预扣一旦发生，就必须有对应的结算，否则那笔钱一直挂着。放进 defer 之后，转发过程中即使 panic，钱也会退回去。

**金额用整数微元。** 1 微元 = 0.000001 元。配置里的单价单位是"元每百万 token"，常带小数（DeepSeek 的缓存命中价是 0.14），启动时把它乘以 10⁶ 换算成整数的"微元每百万 token"，之后算费用只有整数乘除：`(token 数 × 单价 + 10⁶ - 1) / 10⁶`，除法里顺带向上取整到 1 微元。

浮点只出现在读配置的那一次换算里。如果留着 float64 一路算到费用，`50 × 0.14` 会得到 7.000000000000001，向上取整就变成 8 微元——每次都往贵了收 1 微元。

**收口断言是一个可以对账的测试**（`cmd/gateway/main_test.go`）。两个网关实例各开一套数据库连接、共用一套 MySQL，1000 个并发请求打同一个 Key。每次请求的两个金额是确定的：消息只有 1 个字符，网关的估算和 mock 上游报告的 prompt token 都是 1；模型的默认输出上限是 5，所以预扣 42 微元，而 mock 只回 3 个 token，实际费用 26 微元，每次结算都要退回 16 微元。余额充到正好够预扣 500 次。

退回的差额会让后面的请求又扣得下，所以成功的次数不是一个定值，断言落在两条必须成立的性质上：

- **零超扣**：最后的余额不能是负数；
- **账目守恒**：余额加上所有用量记录的费用，必须正好等于充值的金额。

再加上几条对得上的账：成功数加被拒数等于 1000、用量记录数等于成功数、每条记录的费用都是按实际用量算的，以及成功次数落在 `[充值额/预扣, 充值额/实际费用]` 这个算得出来的区间里。

两次破坏性验证说明断言确实卡在要害上，而不是碰巧通过：把预扣改成"先查再改"，余额被扣到 -1646，零超扣这条失败；把结算里退回差额的那句 UPDATE 删掉，守恒这条失败（21000 变成 13000）。

## 取舍

- **预扣按输出上限，不按实际。** 代价是请求进行期间余额被多占一部分：把输出上限设得很大的请求，即使实际用不了那么多，也可能因为余额不够预扣而被拒。换来的是余额不会被打穿。
- **结算是同步的。** 调用方要等结算写完数据库才看到响应结束。好处是结算失败时立刻知道，不用另做一套补偿；代价是每个请求末尾多出一次数据库往返。`BenchmarkReserveAndSettle` 量过：本机连 docker 里的 MySQL，预扣约 2.9 ms、结算约 2.0 ms，而一次 LLM 回答要几秒，这点开销可以接受，所以没有改成异步。网关整体多出的延迟由 M4 的压测给出。
- **透支只能来自 prompt 估少了。** 输出有上限兜底，prompt 没有，所以估算偏低时余额会变成负数。ADR 选择照实扣，这个 Key 的下一次预扣自然会失败。
- **结算失败只记日志，不重试。** 数据库这时多半已经连不上，重试大概率也失败，而调用方的响应早就发完了。日志里带上请求 ID、模型、预扣金额和用量，错误信息里带上 API Key 的 ID（`relay` 只认识 context 里的 Key，不认识它的 ID，所以由 `billing` 包进错误里），够人工对账；自动补偿要引入一张待结算表和一个后台任务，和"进程崩溃不补偿"是同一个取舍。
- **`billing` 不认识 `relay`。** 两个包各自定义 `Reservation` 和 `Result`，字段一样，由 `cmd/gateway` 里的适配器直接转换。多写十来行，换来业务包之间没有横向依赖；字段哪天对不上了，转换那行就是一个编译错误。
- **进程崩溃不补偿。** 结算之前进程被 kill -9，那笔预扣就留在那里，等于按预扣金额收费。要修就得把预扣单独记一张表、再加一个回收的定时任务，目前不值得。
- **优雅退出时先取消再结算。** 收到 SIGTERM 后先等进行中的请求自己结束，超过 30 秒还没结束的，网关取消它们的 context，让它们按"中途断开"的规则结算完再退出。
- **两个包写同一张表。** `api_keys` 的余额由 `billing` 改（预扣、结算），其余字段由 `apikey` 改（创建、充值、禁用）。分开是因为预扣和结算必须和用量记录在同一个事务里，而创建和禁用不需要。

## 延伸问题

- 同一个 Key 的并发极高时会怎样？所有预扣都排在同一行的行锁上，这一行会成为热点。ADR-0002 记了一个不实现的演进方向：余额搬进 Redis、用 Lua 预扣，再定期同步回 MySQL。
- 为什么不用 `SELECT ... FOR UPDATE` 再改？那要两次往返，而且事务开着的时间更长；一条 UPDATE 就能同时完成判断和扣减。
- 退款和调账怎么做？现在只有充值。补一张流水表、把余额算成流水的和，是常见做法，代价是每次读余额都要聚合。
- 用量记录会一直涨，怎么办？按月分区或者定期归档，查询都带 `api_key_id` 和时间范围，走的是那条复合索引。
