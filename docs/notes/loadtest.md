# 首 token 延迟压测

## 问题

要回答的是一句话：**调用方把请求从直连上游改成经过网关，多等多久才看到第一个字？**

难在这两个量差着两个数量级。网关做的事是几次 Redis 往返、一条 PostgreSQL 的 UPDATE 和一次转发，加起来是毫秒级；而上游生成第一个 token 要几百毫秒，并且抖得厉害——实测同一个上游、同样的请求，首 token 延迟在 325 毫秒到 4 秒之间。直接各打一轮再相减，减出来的是上游的脾气，不是网关的开销。

## 方案

**主口径打 mock 上游**（`cmd/mockupstream`），它的首 token 延迟是配死的常数。两端的上游行为完全一样，差值里剩下的就只有网关。真实上游另跑一组，用途是验证整条链路在真实上游上成立，不用来出数字。

**测的是第一个 SSE 事件到达的时间**，不是整段读完（`cmd/loadtest/run.go`）。网关的开销全部发生在转发的路上，后面的事件只是沿着同一条已经建好的流走，算进来只会稀释要看的那个数。

**两端交替打，而不是先跑完一端再跑另一端。** 上游的延迟随时间漂移，分开跑的话两组经历的是不同的时间窗口，差出来的是漂移。每一对内部的先后也轮换，免得固定排在后面的那端总沾到前一次刚热好的连接。

这条有测试钉着（`TestBothSidesShareTheSameTimeWindow`）：mock 前 20 个请求快、之后突然变慢，交替打时两端各摊到一半快的一半慢的，差值接近零。把实现改成"先跑完一组再跑另一组"，同一条断言测出 **180 毫秒**的假差值，直接失败。

**分位数用最近秩法，不在相邻样本之间插值**：报出来的数字一定是真发生过的某一次请求。

**失败的请求算错误，不算样本。** 失败返回得比成功快得多，混进样本里会把分位数拉得很好看。一旦出错就停下，因为这批数据已经不可信了。

**连接池要装得下所有 worker。** `http.Transport` 默认每个主机只留 2 条空闲连接，并发一高就每次重新建连，测出来的成了握手时间。另外每次都要把剩下的流读完再关：半路 `Close` 会切断连接，下一次请求同样要重新握手。

## 实测

mock 上游首 token 固定 300 毫秒，500 对请求、20 并发，两端都在同一台开发机上：

```
                N      min      p50      p90      p99      max
      direct  500  300.1ms  300.6ms  301.5ms  303.2ms  303.3ms
     gateway  500  302.3ms  308.1ms  319.6ms  334.8ms  347.3ms
  gateway 多出        +2.1ms   +7.5ms  +18.1ms  +31.6ms  +43.9ms
```

**P99 多出 31.6 毫秒**，中位数多出 7.5 毫秒。

这个尾巴是网关的固有开销，还是排队？把并发从 20 降到 5 再跑一轮：P99 的差从 +31.6ms 掉到 **+18.3ms**，而 min 几乎不动（+2.1ms → +2.3ms）。

两个数合起来说明：**固有开销约 2 毫秒，尾部主要是排队**。压测全程打的是同一个 API Key，预扣是一条带条件的 UPDATE，同一行上的并发预扣被行锁排成队（见 [ADR-0001](../adr/0001-reserve-then-settle.md)），并发越高排得越长。这正是该由压测暴露出来的东西——它是设计的直接后果，不是实现里的意外。

真实上游那一组（阿里云百炼的 OpenAI 兼容接口，`max_tokens: 1`）跑了三轮，每一轮都在说同一件事：

| 样本 | 发送方式 | min | p50 | p90 | p99 |
|---|---|---|---|---|---|
| 10 对 | 每 3 秒一个请求 | -25.4ms | -124.6ms | -1.3202s | -3.1356s |
| 100 对 | 每 3 秒一个请求 | +61.5ms | +26ms | +137.1ms | +1.0877s |
| 8 对 | 连续打 | -25ms | +19.9ms | -937.1ms | -937.1ms |

同样的两端、同样的请求，P99 的差在 **-3.1 秒和 +1.1 秒之间摆**，而要测的开销是 2 毫秒。

连 min 也靠不住。第二轮的 min 差是 +61.5ms，看着像某种固定成本（比如网关到上游那一跳的 TLS 握手没复用上——限速到 3 秒一个请求时，连接在池子里要躺 6 秒）。第三轮特意连续打，让连接一直是热的，min 差却翻成了 -25ms。所以那 61.5 毫秒是噪声，不是成本：min 是"这批样本里上游状态最好的那一次"，两端各取各的，依然是两次不同的观测。

上游自己的首 token 延迟在 325 毫秒到 4 秒之间，这股噪声比要测的信号大三个数量级。这组数据的用处正在于此——它说明为什么主口径必须用 mock。

## 吞吐

延迟回答"一个请求慢多少"，吞吐回答"每秒能处理多少个、卡在哪"。这两件事要分开测，连上游都得换一种配法：**mock 不加任何延迟**（首 token 延迟 0、只吐一个 token）。加了延迟的话，打满并发后的吞吐就等于"并发数除以延迟"，量的是上游而不是网关。

两端也不再交替，各自跑满一段时间。交替的意义是抵消上游随时间的漂移，而吞吐只对 mock 有意义，mock 的行为不随时间变，分开跑才能各自打满并发。

50 个并发，每端 20 秒：

| 被压的一端 | QPS | p50 | p99 |
|---|---|---|---|
| mock 上游（对照） | **60,763** | 0.7ms | 2.5ms |
| 网关，20 个 Key | **3,192** | 14.3ms | 36.6ms |
| 网关，全部打同一个 Key | **565** | 80.4ms | 222.9ms |

对照那一行的用处是证明瓶颈不在 mock：它能跑到网关的十九倍。

**瓶颈是 PostgreSQL。** 压测打网关那一端时，PG 容器的 CPU 占到 **95.5%**，Redis 只有 13%。一个请求要写两次库——预扣一条 UPDATE，结算和用量记录一个事务——3192 × 2 差不多是每秒 6400 个事务，本机 Docker 里开着 fsync 的 PG 就是这个量级。

把连接池从 20 条放到 60 条，QPS 只从 3192 涨到 3694（**15%**），p99 从 36.6ms 降到 27ms。所以"一个实例最多占 20 条连接"这个限制没有卡住吞吐，而它换来的是多起几个实例也不会占满 PostgreSQL 默认那 100 条连接。这个取舍是划算的，所以没有改。

**同一个 Key 和 20 个 Key 差 5.7 倍**（565 对 3192），这是预扣行锁的直接代价：同一行上的并发预扣被数据库排成队。延迟那一节里"尾部是排队"的结论，到这里才算有了直接证据——那边只能从"min 不动、P99 随并发涨"倒推。

顺带验证了一下测量本身：50 个并发除以 3192 QPS 是 15.7 毫秒，和实测的 p50 14.3ms 对得上（Little's Law）。压测程序没有在自己这边制造瓶颈。

## 取舍

- **报的是两条分布的 P99 之差，不是配对差值的 P99。** 后者更严格，但一对里的两次请求打的是上游的两个不同时刻，配对差值里混着上游自己的抖动，尾部会被这股噪声撑大。分布之差回答的是"网关这一端的尾部体验差多少"，这更接近调用方真正感知到的东西。
- **遇到错误就停，不容忍错误率。** 压测中途出错说明环境已经不对了（限流、余额、上游拒绝），继续跑只会产出一份看着正常的坏数据。代价是长时间的压测可能因为一个 429 白跑，所以真实上游那组要先用 `-interval` 把速率压到限制以内。
- **吞吐只对 mock 测，而且只当成"瓶颈在哪"的答案。** 3192 QPS 这个绝对值换台机器就变，它的用处是指出 PG 是瓶颈、行锁值 5.7 倍、连接池只值 15%。真实上游的速率限制会先一步成为瓶颈，那边测不出网关的能力。
- **mock、网关、PostgreSQL、Redis 和压测程序全在一台机器上，互相抢 CPU。** 绝对值会比分开部署时差，但两端抢的是同一份 CPU，差值仍然可比。
- **请求体两端完全一致，`-extra` 只能往上加字段。** 核心字段在 extra 之后写，所以 `stream` 改不掉——压测的前提是流式。

## 延伸问题

- 想把尾部再压下去该动哪里？先动预扣：同一个 Key 的并发预扣挤在一行上，实测值 5.7 倍吞吐。可以给热点 Key 分片（一行拆成 N 行、随机挑一行扣），代价是查余额要把 N 行加起来。
- PG 的 CPU 已经 95% 了，再往上要动的是写库的次数：一个请求两个事务能不能并成一个？不能——预扣必须在转发之前，结算必须在之后。能减的是用量记录，攒一批再写，代价是崩溃时丢掉最后一批记录，而余额本身不受影响（它和预扣在同一条 UPDATE 里）。
- 为什么不测非流式的延迟？非流式要等整个回答生成完，那个时间由上游决定，网关的两毫秒淹没在里面，测了也看不出什么。
- 真实上游的对照怎么做才有意义？得让两端在同一时刻打同一个上游，例如把一对请求并发发出而不是顺序发出，这样两端遇到的上游状态最接近。代价是并发翻倍，对有速率限制的上游不友好。
- 分位数只有 500 个样本，P99 落在第 495 个，本身抖动不小。要让 P99 稳下来得上万个样本；mock 那组加大 `-n` 就行，真实上游那组受速率限制做不到。
