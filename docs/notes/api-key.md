# API Key 与鉴权

## 问题

调用方凭 API Key 访问网关，这个 Key 决定了鉴权结果和扣谁的钱。它要满足几点：

1. 库被拖走也不能让人拿着数据直接调用；
2. 鉴权在每个请求的热路径上，不能慢；
3. 管理员要能创建、充值、禁用，但普通调用方碰不到这些操作。

## 方案

**Key 的格式是 `sk-` 加 32 字节随机数**（`crypto/rand`，base64 编码）。数据库里只存它的 SHA-256，明文只在创建时返回一次，丢了只能重新建。理由见 [ADR-0003](../adr/0003-api-key-sha256.md)：Key 本身有 256 位熵，穷举不可行，用 bcrypt 这类慢哈希只会拖慢每一次鉴权，而且加盐之后没法按哈希建唯一索引。

**鉴权是一次按唯一索引的等值查询**（`internal/apikey/auth.go`）：从 `Authorization: Bearer` 取出明文，算一次 SHA-256，按 `key_hash` 查一行。通过之后把 **Key 的 ID** 放进请求的 context，后面的日志和计费只认这个 ID，明文再也不出现。

**Key 不存在和被禁用分开报错**：前者 401 `invalid_api_key`，后者 401 `key_disabled`。调用方由此知道是该换一个 Key，还是该去找管理员。

**被禁用的 Key 有两道关**：鉴权时查到 `disabled` 直接拒绝；预扣的那条 UPDATE 里也带着 `NOT disabled`。第二道关是为 M3 准备的——那时鉴权会走缓存，缓存可能是旧的，而预扣读的永远是数据库里的最新状态。

**管理接口单独一个端口**（默认 `:8081`），凭管理员密钥访问，密钥同样只从环境变量读。比较用 `subtle.ConstantTimeCompare`，避免按耗时逐字节猜。四个接口：创建 Key、查余额和状态、充值、禁用。

**禁用不是删除**：余额保留，用量记录也留着，`api_keys` 是用量记录的外键目标。

## 取舍

- **明文只返回一次。** 管理员得自己保存好，网关帮不上忙。换来的是库里没有任何可以直接拿去用的凭证。
- **充值的单位是微元。** 管理接口直接收 `amount_micro`，不做"元"的换算，接口和存储的单位一致，不会出现四舍五入带来的差额。代价是调用管理接口的人要自己乘 10⁶。
- **没有列出所有 Key 的接口。** 目前只按 ID 查。需要看全部时直接查库，省下分页和过滤的一套代码。
- **管理员密钥是一个固定的字符串，没有多管理员和权限分级。** 这是一个单体网关的运维口子，不是一套账号体系。
- **两个端口共用同一套公共中间件**（请求 ID、访问日志、panic 恢复），只是鉴权中间件不同。

## 延伸问题

- 每个请求都查一次数据库，扛得住吗？这正是 M3 要做的鉴权缓存：Redis，TTL 5 分钟，禁用时主动删除。缓存不一致的窗口由预扣时的 `NOT disabled` 兜住。
- Key 泄露了怎么办？现在只能禁用再建一个。常见做法是支持一个 Key 有多个"版本"，或者给 Key 加上过期时间。
- 怎么在界面上认出一个 Key？通常存一段前缀（例如 `sk-abcd…`）单独展示。本项目连这个也没存，只能靠创建时填的备注。
- 为什么不用 JWT？JWT 自带过期和载荷，不用查库，但没法即时禁用，而且余额本来就要查库，省不掉这一次往返。
