# 用量采集与估算

## 问题

计费要知道每次请求用了多少 token。最准的数字来自上游，但上游并不总会报告：流式请求默认不带用量；调用方中途断开或上游中途出错时，流在报告用量之前就断了。网关要在每种结局下都给出一个用量，并且标明它是上游报告的还是网关估算的。

## 方案

`internal/relay/usage.go` 里的 `meter` 负责采集，每次转发创建一个：

- 创建时统计请求里所有消息的文本字符数，用来估算 prompt token；
- 转发过程中，`observe` 接收每一段转发给调用方的响应，记下上游报告的用量，同时统计回答文本（`content`、`reasoning_content`、工具调用的参数）的字符数，用来估算 completion token；
- 转发结束后，`usage` 按下表给出结算用的用量。

| 情形 | 用量 | 来源 |
|---|---|---|
| 上游报告了用量 | 上游的数字 | 上游报告 |
| 调用方中途断开 | 估算的 prompt + 按已转发内容估算的 completion | 估算 |
| 上游中途出错，调用方已收到部分回答 | 同上 | 估算 |
| 上游出错，调用方什么也没收到（包括上游返回错误状态码） | 零 | 估算 |

估算的比例取自 DeepSeek 文档：1 个英文字符约 0.3 个 token，1 个中文字符约 0.6 个 token。实现时 ASCII 字符都按英文算、其余都按中文算，用整数运算 `(3×ASCII 字符数 + 6×其他字符数 + 9) / 10` 向上取整，避开浮点。

结果以 `relay.Result` 交给 `Biller` 接口。这个接口由 relay 自己定义，只含 relay 需要的方法；M1 里 `cmd/gateway` 注入一个只打日志的实现，M2 换成真正的计费。

## 取舍

- **粗估，而不是用 tokenizer 精确计数。** 各家模型的 tokenizer 不同，引入分词库既增加依赖，又拖慢每个请求。估算只在上游没报告时才用，偏差由结算规则兜住，系数在 M2 对照真实上游校准。
- **只数文本。** 图片、工具定义（`tools`）、`response_format` 里的 JSON Schema 都占 prompt token，但没法按字符数估，这里没有算。
- **什么也没收到就按零算。** 调用方拿到的是一个错误，不收费最合理；代价是上游可能已经为 prompt 向网关收了钱，这部分由网关承担。
- **用量来源用一个布尔值表示。** 结算只需要区分"上游报告"和"网关估算"，布尔值足够，落库时再映射成可读的字符串。

## 延伸问题

- 系数怎么校准？用真实上游跑一批中英文请求，对比上游报告的 prompt token 和网关的估算值，M2 会做一次。
- DeepSeek 的缓存命中 token（`prompt_cache_hit_tokens`）单价更低，要不要区分？目前按统一的输入单价计费，区分缓存命中是后续的改进。
- 推理模型的思考过程（`reasoning_content`）按输出计费，所以估算时一并计入 completion token。
- 估算出的 completion token 可能超过输出上限。M2 结算时要把它截断到输出上限，才能保证透支只可能来自 prompt token 估少了（见 ADR-0001）。
