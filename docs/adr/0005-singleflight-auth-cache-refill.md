# 鉴权缓存的回源用 singleflight 合并，TTL 带随机偏移

鉴权缓存挡在每一个请求前面，所以它过期的那一刻要算清楚。缓存里没有这个 Key 时的穿透已经处理过（把"不存在"也记 30 秒），剩下两个都发生在并发下：一个高频 Key 的缓存过期的瞬间，所有在飞的请求会一起回源打数据库（击穿）；一批同时建出来、同时开始被调用的 Key，缓存的 TTL 是个定数的话会在同一刻集体过期（雪崩）。

**同一个哈希的并发回源合并成一次，用 `golang.org/x/sync/singleflight`。** 它是选型表之外的第一个依赖，此前已经作为 indirect 出现在依赖图里（go-redis 用它），升级成直接依赖不增加构建负担。自己写一遍要处理等待、结果分发和 panic 传播，而它的语义正好就是这件事，不值得重写。

**合并出来的那次查询不跟着任何一个调用方的请求取消**：`context.WithoutCancel` 加一个自己的超时。结果是所有在等的请求共用的，先到的那个断开连接不该把别人的查询一起取消；脱开之后就得有个上限，和删缓存那一步是一个道理。等待仍然按各自的 context 结束，一次慢查询拖不住别人。

**写缓存时从 TTL 上减一个 `[0, 30 秒)` 的随机偏移**，偏移量由外面注入：生产用 `RandomJitter`，测试注入固定值，TTL 才是个确定的数，和令牌桶注入时间是同一个做法（[ADR-0004](0004-per-key-token-bucket.md)）。偏移**只减不增**：TTL 是禁用主动失效的兜底上限，"删缓存失败时最多陈旧 5 分钟"这句话因此不用改口。取 TTL 的十分之一是折中——摊得再开一些，平均 TTL 就短一截，白白多回源几次。

代价是合并窗口内到达的请求共用同一份结果：这次回源如果读到的是禁用前的旧值，看到旧值的请求就比原来多。窗口只有一次查询那么长，而且和已有的缓存回填竞态是同一个窗口，没有新增一种不一致；被禁用的 Key 即使穿过鉴权，也会被预扣的条件 UPDATE 挡下，见 [ADR-0001](0001-reserve-then-settle.md)、[ADR-0002](0002-balance-in-mysql-only.md)。
