# 余额只存在 PostgreSQL，Redis 只做鉴权缓存和限流

余额是账，只能有一份权威数据，所以只存在 PostgreSQL 里。预扣是一条带条件的 UPDATE：余额够、并且 Key 没有被禁用才扣，用 RowsAffected 判断成败，而不是先查再改。同一个 Key 的并发预扣由行锁排队，多个网关实例之间不需要额外协调。结算和用量记录在同一个事务里提交。

Redis 只做两件事，里面的数据丢了都能重建：

- **鉴权缓存**：Cache-Aside，TTL 5 分钟。缓存里只放 Key 的身份信息和限流参数，不放余额。查不到的 Key 也记 30 秒，否则拿随机 Key 反复打过来每次都要查一趟数据库；代价是"先查后建"的 Key 最长 30 秒不可用，管理接口创建时会顺手清掉这个记号。禁用 Key 时先改 PG，再删缓存。并发的缓存回填可能把禁用前的旧值写回去，最长持续一个 TTL；但预扣的条件 UPDATE 会检查禁用状态，被禁用的 Key 照样过不了预扣，旧缓存只影响不计费的 `GET /v1/models`。
- **限流**：按 Key 的令牌桶，用自己写的 Lua 脚本在 Redis 里一次完成补充和扣减，多个网关实例共享同一个桶。

**Redis 不可用时放行。** 限流脚本执行失败（Redis 宕机、超时）时请求照常通过，并记一条 warn 日志；鉴权缓存读不到就直接查 PG。能这样做是因为余额不在 Redis 里：预扣照样走 PG 的条件 UPDATE，Redis 故障不会造成超扣，损失的只是故障期间按 Key 的限流。反过来拒绝请求的话，Redis 一出故障整个网关就不可用了。

演进方向（不实现）：同一个 Key 的并发极高时，PG 的行锁会成为热点，可以把余额搬进 Redis、用 Lua 预扣，再定期同步回 PG 并核对。代价是出现两份余额，要处理两者不一致；目前的并发量用不到。
