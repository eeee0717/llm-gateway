# 计费采用先预扣、后结算

一次请求的费用要等请求结束才知道，流式请求可能持续几十秒。如果结束后才扣，同一个 API Key 的并发请求在余额耗尽之前会全部放行，余额被打穿。因此每次请求在转发前按最大可能的费用预扣，余额不够就拒绝；结束后按实际费用结算，多退少补。代价是请求进行期间余额被多占一部分：输出上限设得很大的请求，即使实际用不了那么多，也可能因为余额不够预扣而被拒绝。

具体规则：

- **预扣金额** = 估算的 prompt token × 输入单价 + 输出上限 × 输出单价。prompt token 按字符数粗估，系数对照真实上游校准。调用方没有指定输出上限时，网关用模型的默认输出上限，并把它写进发给上游的请求，保证 completion token 不超出预扣时的假设。
- **上游没有报告用量**：调用方中途断开时立即取消上游请求；中途断开或流中途出错时，completion token 按已转发的内容、用同一个方法估算（不超过输出上限），然后结算。用量记录标明用量来源：上游报告，还是网关估算。上游在输出任何内容之前就返回错误时，按零用量结算，预扣全额退回。
- **透支**：实际费用超过预扣时照实扣，余额可以变成负数，这个 Key 的下一次预扣自然会失败。按上面的规则，透支只可能来自 prompt token 估少了。
- **进程崩溃**：结算之前进程崩溃时不做补偿，结果等于按预扣金额收费，并且没有用量记录。正常退出时等所有进行中的请求结算完。另一种做法是把预扣单独记成一张表，由定时任务回收崩溃遗留的预扣，但要多一张表和一个后台任务，目前不值得。
- **金额**：余额以整数微元存储（1 微元 = 0.000001 元），避开浮点误差；单价在配置里的单位是元/百万 token；每次结算的费用向上取整到 1 微元。
- **幂等**：用量记录以请求 ID 为唯一键，和余额变更在同一个事务里写入，重复结算不会重复扣钱。请求 ID 由网关生成，不沿用调用方传来的值，以免不同请求撞上同一个键。
